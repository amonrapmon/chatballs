# Почтовое продолжение веб-диалога

Серверная часть SPEC-0031 использует штатные EMAIL-подключения, inbox и outbox.
Новый интерфейс и сбор браузерных сигналов в эту реализацию не входят.

Все адреса ниже относительны к
`/api/v1/organizations/{organization_public_id}/conversations/{conversation_id}/`.
Организация определяется проверенной membership, а не телом запроса.

| Метод и путь | Доступ и результат |
| --- | --- |
| `GET email/options/` | Право ответа; сохранённые адреса контакта и активные настроенные ящики организации. Только id, название и адрес ящика; конфигурация и секрет не выдаются. |
| `POST email/operations/` | Право ответа, открытый WEB-диалог; атомарная операция, публичное сообщение, Message-ID, попытка и tenant outbox. |
| `GET email/operations/?before={id}&limit=50` | Текущая видимость диалога; операции с безопасным журналом попыток, курсор `nextCursor`. |
| `POST email/operations/{operation_id}/retry/` | Текущее право ответа и принадлежность операции диалогу; новая попытка того же сообщения, Message-ID и ящика. |
| `GET visitor-state/` | Текущая видимость; раздельные наблюдения вкладок точной WebSession исходного WEB-подключения и идентичности. Credential сессии не выдаётся. |

Тело отправки:

```json
{
  "recipient": "customer@example.org",
  "connectionId": 123,
  "text": "Ответ сотрудника",
  "subject": "Тема обращения",
  "clientKey": "уникальный-ключ-запроса"
}
```

Тема необязательна: используется существующая переводимая тема письма на языке
организации. В теме запрещены CR/LF. Текст ограничен 20 000 символами, ключ —
128, тема — 998. Адрес принимается только из текущего `Contact.email` или
существующей EMAIL-идентичности этого контакта. Нужны активное подключение и
агентский канал, адрес ящика, IMAP/SMTP-хосты и секрет; демо-подключения исключены.
Проверка конфигурации не обещает доступность удалённого SMTP-сервера.

Первый запрос возвращает `201`, повтор того же ключа и содержимого — `200` с
той же операцией. Другое содержимое с этим ключом возвращает `409`. Ключ уникален
в организации; конкурентные запросы сериализуются до создания сообщения.
Первый ответ атомарно берёт диалог у AI/очереди по существующему механизму.
В HUMAN-диалоге отвечают ответственный, активный участник или руководитель организации;
управленческий доступ супервизора сам по себе не разрешает ответ.
Почтовый ответ использует общий серверный сервис проверки ответа. Первое письмо
назначенного сотрудника подтверждает принятие диалога так же, как обычная реплика;
участник отвечает без смены ответственного. Удаление участника блокирует ещё не
начавшуюся SMTP-отправку при повторной проверке прав в outbox.

Попытки хранят `PENDING`, `SENDING`, `SMTP_ACCEPTED`, `FAILED`, `UNKNOWN`,
время создания/начала/завершения, инициатора и только разрешённый код ошибки.
Сырой текст SMTP-ошибки не сохраняется и не выдаётся. Outbox хранит техническое
исполнение события отдельно от результата попытки. Ошибка SMTP не запускает
скрытую новую отправку: сотрудник явно повторяет операцию. Сбой подключения или
авторизации до отправки — ошибка, отрицательный SMTP-ответ — отказ, потеря соединения во время отправки —
неизвестный исход. Финальный успех SMTP остаётся успехом даже при сбое QUIT.

Повтор допустим, только если все прошлые попытки закончились ошибкой или
неизвестным исходом. `PENDING`, `SENDING` и достоверное `SMTP_ACCEPTED` блокируют
повтор. Для `UNKNOWN` требуется `{"acknowledgeUnknown": true}`: возможно получение
двух писем. Новый ящик этим запросом не выбирается. Перед фактической отправкой
воркер повторно проверяет текущие права инициатора и доступность прежнего ящика.
Повторная обработка завершённой попытки ничего не отправляет; прерванная отправка
после истечения штатной аренды outbox становится `UNKNOWN/WORKER_INTERRUPTED`.
Если повторная обработка попала перед истечением аренды самой попытки, событие
возвращается в штатный механизм повторов outbox, без второй SMTP-отправки и без
ложного завершения выполняющейся попытки. `retryAllowed` также учитывает текущую
доступность сохранённого ящика.

`SMTP_ACCEPTED` означает принятие сервером почты, а не доставку или прочтение.
API всегда возвращает `deliveryConfirmed: false`: в текущем контуре нет
поддерживаемого достоверного события доставки.

Входящий адаптер передаёт `In-Reply-To` и `References`. Маршрут использует
реестр Message-ID выбранного ящика и проверяет сохранённого отправителя.
Повтор входящего Message-ID не создаёт сообщения. Письмо без подходящей связи,
от другого отправителя или в другом ящике идёт по прежнему EMAIL-потоку.
Совпадение email контактов не объединяет их и не создаёт EMAIL-идентичность
для веб-контакта. Исторический адрес треда продолжает принимать связанные
ответы после изменения адреса в карточке контакта.

После завершения создаётся новый диалог с `previous_conversation`, прежними
WEB-подключением, каналом, контактом и группой, в очереди сотрудников.
Старый диалог не открывается заново. Дополнительный тред наследует точный
маршрут через `previous_thread`; БД проверяет закрытого предшественника,
tenant, контакт и маршрут. Последующие ответы в старый тред используют уже
созданный преемник. Удаление прежнего диалога не удаляет историю преемника.
Входящий EMAIL-ответ не запускает автоматический ответ через WEB-транспорт.
Создание преемника и вход в очередь фиксируются общими событиями `FOLLOW_UP`
и `QUEUE_ENTERED` с фактическим EMAIL-подключением; уведомления используют общий
механизм входящих сообщений.

Публичная веб-история по прежнему содержит публичный почтовый ответ, без
журнала попыток. История сотрудников дополнена полем `transport` у связанных
писем. Публичные почтовые факты сохраняются в `ConversationEvent` с фактическим
EMAIL-подключением и исходными измерениями диалога; повтор попытки не создаёт
второй факт человеческого ответа. Полная статистика других источников не
объявляется покрытой этими событиями.

Проверки запускаются в штатном управляемом окружении через `backend-admin`.
Новая миграция добавляет только nullable-связь преемника и проверки БД.
Миграции `conversations/0041` и `tenancy/0060` соединяют её с актуальной историей
`main`, сохраняя имена уже применённых миграций этой задачи.
Первый прогон после изменения схемы использует `--create-db`, последующие —
`--reuse-db`. Тестовые записи создаются только в изолированной Django test-БД;
seed, учётные данные рабочей базы и отдельные SMTP/API-серверы не используются.
Unit-тесты SMTP проверяют адаптер на границе стандартного
библиотечного клиента; это не проверка доставки реальному адресату.
