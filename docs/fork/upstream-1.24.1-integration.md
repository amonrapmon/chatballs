# Интеграция Chatballs upstream v1.24.1

## Состав слияния

Основа форка — `c49e0d061e38f67f0fe195618250bdfd706520f6`. Второй родитель — тег `v1.24.1` и вершина чистой vendor-ветки `vendor/upstream-v1.24.1` на `d461f101c830dca82fc6c7e9144b16ee922fe763`. Относительно предыдущей vendor-базы пришли 13 коммитов. North Wind и коммиты после v1.24.1 находятся за границей слияния.

- В `run_worker.py` роли `poller` и `all` выполняют check-in и подключаются к SSE Backoffice при включённых внешних проверках. Роли `events` и `all` по-прежнему обрабатывают outbox и повторяют отложенные события Native Mirror.
- В `ReportFilters.tsx` оформление фильтров и кнопки сброса взято из v1.24.1. Выбор мессенджера использует фактический тип подключения. Green API Telegram и MAX передаются в API отчёта со своим ID подключения и историческим транспортом `API_CONNECTOR`. Если для точного отчёта нужно выбрать одно из нескольких подключений, интерфейс сохраняет это требование.
- В автоматически объединённом каталоге аудита проверен ключ увольнения и его перевод на оба языка. В стилях интеграций новый минимальный размер применяется к списку серверов MCP и HTTP. В каталогах frontend добавлены симметричные ключи сотрудников и обновлений. Контракт API Connector, внешний Green Adapter и применённые миграции сохранены.
- В типизированную схему результатов нативных действий с сотрудниками добавлены `dismissedAt` и `permissions.canDismiss` с переводами. Эти поля из upstream-ответа нужны для прохождения строгой проверки результата существующих операций.

## Миграции

На чистом PostgreSQL 16 с pgvector применился полный граф. На отдельной базе с кодом форка 1.22.0 применились ровно восемь новых миграций — `identity/0050`, `identity/0051` и `updates/0002`–`0007`. `migrate --check` и `makemigrations --check --dry-run` прошли на обеих базах. Django также прошёл `manage.py check` на чистой базе.

На обновлённой базе под `chatballs_app` прочитаны два синтетических подключения Telegram и MAX, их конфигурация, зашифрованный секрет, контакты, диалоги, сообщения и настройки установки. Запрос к подключениям без tenant context вернул пустую выборку. Пробное клонирование через `pg_dump` / `pg_restore` и `prepare_installation_copy` сменило UUID, сбросило состояние check-in и отключило внешние проверки.

## Backoffice и глобальные права

- Внешние проверки выключены по умолчанию, включая запуск до появления строки настроек. Штатный переключатель управляет check-in, SSE, фоновой и ручной проверками GitHub. После включения check-in отправляет UUID, версию и пригодный публичный адрес, если он задан. Успешная отметка планируется раз в сутки. Смена версии инициирует отметку с прежним UUID, с учётом действующей резервации и `Retry-After`. SSE передаёт UUID и версию и доставляет расписание публикаций.
- `identity/0052_external_checks_off_by_default` однократно отключает унаследованное `true` при ревизии `0` как при переходе с 1.22.0, так и поверх уже применённых миграций 1.24.1. Переключение в интерфейсе меняет ревизию, поэтому зафиксированный выбор сохраняется. В исходной 1.24.1 повторная отправка уже включённого значения через API оставляла ревизию `0` и для миграции выглядит как исходное умолчание. Обратное применение миграции возвращает прежний default в модели миграций, сохраняя текущие значения строк.
- Активный владелец или администратор хотя бы одной организации получает доступ к глобальным настройкам. Изменение публичного адреса, SMTP, языка установки и внешних проверок затрагивает все организации. Также доступны проверка и запрос установки обновления при работающем updater. TURN и хранилище требуют отдельно назначенного администратора установки. Это изменение модели доверия важно для инсталляций с независимыми клиентами.
- Общий выключатель останавливает проверки, но не служит сетевым барьером. Установка уже известной версии через работающий updater проверяется по отдельным условиям. В лаборатории updater оставался выключен, а backend-проверки выполнялись во внутренней Docker-сети без внешнего маршрута. Реальные запросы к Backoffice в тестах не выполнялись.

## Проверка после смены умолчания

### Миграции

На PostgreSQL 16 с pgvector базы подготовлены соответствующим историческим кодом. База форка с `c49e0d06` получила девять миграций, а на базе с `720fdfb0` применена только `identity/0052`. На обеих сохранился адрес синтетической установки, состояние стало `false` с ревизией `0`. На свежей и обеих обновлённых базах прошли `migrate --check` и `makemigrations --check --dry-run`. На свежей базе также прошёл `manage.py check`.

### Production-сборка backend

`docker build --pull -f apps/backend/Dockerfile.production --build-arg CHATBALLS_VERSION=1.24.1 .` прошёл на официальном `python:3.12-slim`. FFmpeg и Python-зависимости установлены штатными шагами Dockerfile. При пересборке с исправлением использован обычный кэш Docker, повторно прошёл `collectstatic` (163 файла скопированы, 469 обработаны).

### Docker Compose

`docker compose config --quiet` прошёл для базового файла и комбинаций с `compose.dev.yaml` и `compose.task.yaml`. Изолированный Compose-проект запустил `secrets`, PostgreSQL, Redis, `init`, обе backend-поверхности, poller и два обработчика событий. Тестовая сеть была внутренней, без исходящего маршрута.

### Readiness и перезапуск

На свежей базе обе поверхности вернули HTTP 200 на `/api/v1/health/ready/` с `database=true` и `redis=true`. До запуска poller строка настроек отсутствовала. После первого цикла и после перезапуска backend и воркеров настройка оставалась `false` с ревизией `0`, строки check-in/SSE отсутствовали, `checked_at` проверки GitHub оставалось пустым. Пробный запрос сразу после перезапуска превысил таймаут 5 секунд во время старта Gunicorn. После перехода контейнеров в `healthy` обе поверхности снова вернули HTTP 200.

### Регрессия внешних проверок

На исходном коде семь новых случаев воспроизвели прежнее поведение. Два сценария сохранения явного выбора прошли. С исправлением прошли все 69 целевых тестов настройки, миграции, GitHub, check-in, SSE, нативных действий установки и воркера на PostgreSQL с `--reuse-db`. Сетевые вызовы проверялись заглушками. Ruff прошёл для всего backend.

## Последующее лабораторное развёртывание

1. Использовать отдельный Compose-проект с собственными томами и тестовыми секретами либо разрешённую синтетическую копию. Проверить `docker compose config --quiet` для точного набора файлов и отключить исходящий доступ backend и воркеров к внешним сервисам до старта.
2. Запустить PostgreSQL и миграции через `init`. На свежей базе внешние проверки уже выключены. Для независимой копии, до запуска воркеров, выполнить на целевой базе `python manage.py prepare_installation_copy --confirm-independent-copy`. Проверить новый UUID и выключенные внешние проверки.
3. Поднять приложение и оба воркера. Оставить updater выключенным. Для тестовых обращений использовать локальный макет Backoffice или моки HTTP. `CHATBALLS_BACKOFFICE_BASE_URL` в режиме DEBUG подменяет адрес только для SSE. Клиент check-in использует фиксированный адрес, поэтому для проверки его HTTP-транспорта нужны моки.
4. Проверить роль `OWNER` / `ADMIN`, увольнение сотрудника с назначенным диалогом, отчёты Telegram и MAX, первый нативный исходящий и вложения на синтетических данных. Для отдельной проверки updater сверить канал релизов одновременно у backend и updater. Значение по умолчанию указывает на `dartdavros/chatballs`.
