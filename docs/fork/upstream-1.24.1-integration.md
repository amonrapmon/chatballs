# Интеграция Chatballs upstream v1.24.1

## Состав слияния

Основа форка — `c49e0d061e38f67f0fe195618250bdfd706520f6`. Второй родитель — тег `v1.24.1` и вершина чистой vendor-ветки `vendor/upstream-v1.24.1` на `d461f101c830dca82fc6c7e9144b16ee922fe763`. Относительно предыдущей vendor-базы пришли 13 коммитов. North Wind и коммиты после v1.24.1 находятся за границей слияния.

- В `run_worker.py` роли `poller` и `all` запускают check-in и SSE-подписку Backoffice. Роли `events` и `all` по-прежнему обрабатывают outbox и повторяют отложенные события Native Mirror.
- В `ReportFilters.tsx` оформление фильтров и кнопки сброса взято из v1.24.1. Выбор мессенджера использует фактический тип подключения. Green API Telegram и MAX передаются в API отчёта со своим ID подключения и историческим транспортом `API_CONNECTOR`. Если для точного отчёта нужно выбрать одно из нескольких подключений, интерфейс сохраняет это требование.
- В автоматически объединённом каталоге аудита проверен ключ увольнения и его перевод на оба языка. В стилях интеграций новый минимальный размер применяется к списку серверов MCP и HTTP. В каталогах frontend добавлены симметричные ключи сотрудников и обновлений. Контракт API Connector, внешний Green Adapter и применённые миграции сохранены.
- В типизированную схему результатов нативных действий с сотрудниками добавлены `dismissedAt` и `permissions.canDismiss` с переводами. Эти поля из upstream-ответа нужны для прохождения строгой проверки результата существующих операций.

На чистом PostgreSQL 16 с pgvector применился полный граф. На отдельной базе с кодом форка 1.22.0 применились ровно восемь новых миграций — `identity/0050`, `identity/0051` и `updates/0002`–`0007`. `migrate --check` и `makemigrations --check --dry-run` прошли на обеих базах. Django также прошёл `manage.py check` на чистой базе.

На обновлённой базе под `chatballs_app` прочитаны два синтетических подключения Telegram и MAX, их конфигурация, зашифрованный секрет, контакты, диалоги, сообщения и настройки установки. Пробное клонирование через `pg_dump` / `pg_restore` и `prepare_installation_copy` сменило UUID, сбросило состояние check-in и отключило внешние проверки.

## Backoffice и глобальные права

- Внешние проверки включены по умолчанию. Check-in отправляет UUID, версию и пригодный публичный адрес, если он задан. Успешная отметка планируется раз в сутки. Смена версии инициирует отметку с прежним UUID, с учётом действующей резервации и `Retry-After`. SSE отдельно передаёт UUID и версию и доставляет расписание публикаций.
- Фоновая и ручная проверка GitHub, check-in и SSE зависят от общего поля `external_checks_enabled`. Сетевые вызовы и состояния GitHub и Backoffice уже раздельны. Независимое управление возможно через отдельные политики для GitHub и Backoffice. Для этого нужно отдельно согласовать значения по умолчанию, миграцию существующего выключателя и обновление API, интерфейса и команды клонирования.
- Активный владелец или администратор хотя бы одной организации получает доступ к глобальным настройкам. Изменение публичного адреса, SMTP, языка установки и внешних проверок затрагивает все организации. Также доступны проверка и запрос установки обновления при работающем updater. TURN и хранилище требуют отдельно назначенного администратора установки. Это изменение модели доверия важно для инсталляций с независимыми клиентами.
- Общий выключатель останавливает проверки, но не служит сетевым барьером. Установка уже известной версии через работающий updater проверяется по отдельным условиям. В лаборатории updater оставался выключен, а backend-проверки выполнялись во внутренней Docker-сети без внешнего маршрута. Реальные запросы к Backoffice в тестах не выполнялись.

Первый frontend-прогон выявил устаревшее ожидание в тесте общего API Connector. Добавлены проверки для двух случаев. Единственное подходящее подключение выбирается автоматически, а при нескольких подходящих требуется явный выбор. В обоих случаях брендированные Telegram и MAX исключены из группы общих подключений.

Полный тестовый набор и подключение к живым провайдерам не запускались. Парный тест с внешним Green Adapter потребовал бы собранный checkout адаптера и отдельную базу. Сборка frontend показала предупреждение Vite о размере чанков и отчёт npm об 11 уязвимостях существующего lockfile, включая 2 критические. Lockfile в слиянии совпадает с исходным `main`.

## Последующее лабораторное развёртывание

1. Использовать отдельный Compose-проект с собственными томами и тестовыми секретами либо разрешённую синтетическую копию. Проверить `docker compose config --quiet` для точного набора файлов и отключить исходящий доступ backend и воркеров к внешним сервисам до старта.
2. Запустить PostgreSQL и миграции через `init`. Для независимой копии, до запуска воркеров, выполнить на целевой базе `python manage.py prepare_installation_copy --confirm-independent-copy`. Проверить новый UUID и выключенные внешние проверки. На свежей базе также применить эту команду для изолированной установки.
3. Поднять приложение и оба воркера. Оставить updater выключенным. Для тестовых обращений использовать локальный макет Backoffice или моки HTTP. `CHATBALLS_BACKOFFICE_BASE_URL` в режиме DEBUG подменяет адрес только для SSE. Клиент check-in использует фиксированный адрес, поэтому для проверки его HTTP-транспорта нужны моки.
4. Проверить роль `OWNER` / `ADMIN`, увольнение сотрудника с назначенным диалогом, отчёты Telegram и MAX, первый нативный исходящий и вложения на синтетических данных. Для отдельной проверки updater сверить канал релизов одновременно у backend и updater. Значение по умолчанию указывает на `dartdavros/chatballs`.
