# Task: CRM Bridge v1 — навигация в YCLIENTS / DIKIDI из Chatballs

**Статус:** согласованная продуктовая задача; реализация не начата, UI-макет подлежит согласованию.  
**Дата:** 2026-10-15.  
**Репозиторий:** `amonrapmon/chatballs`. **Рабочая база на момент подготовки:** `feat/native-mirror-core` @ `e21e7c822d4656d524e688f970fef9154b383f31`.  
**Назначение:** постановка задачи для Codex на отдельный модуль нашего форка; не разрешение на production-деплой.

## 1. Контекст и цель

Chatballs развивается быстро, поэтому собственную функциональность необходимо изолировать от upstream и минимизировать правки его моделей, миграций и UI.

В v1 сотрудник Chatballs открывает карточку контакта и получает ссылку **«Профиль DIKIDI»** или **«Профиль YCLIENTS»**. Ссылка открывает в новой вкладке штатный интерфейс выбранной CRM с **автоматически применённым поиском по телефону контакта**. Оператор затем сам открывает найденную карточку в CRM.

Мы **не реализуем прямое открытие внутренней CRM-карточки по client ID**: проверен именно переход к отфильтрованному списку клиентов, а не прямой маршрут к карточке.

В каждой организации Chatballs активен максимум **один тип CRM**: `NONE`, `YCLIENTS` либо `DIKIDI`. Одна организация может обслуживать несколько филиалов/компаний **того же CRM-провайдера** с разными внешними `company_id`. Мессенджер-подключения (TG/MAX/VK и др.) могут относиться к конкретным филиалам.

**Обязательное бизнес-требование:** в настройках организации Chatballs должен быть явно доступен **ID компании из YC/DIKIDI**. Это **внешний ID**, не внутренний `Organization.id` и не UUID организации Chatballs.

## 2. Проверенные вручную URL и правила

### DIKIDI

```text
https://dikidi.net/ru/owner/clients/?company={external_company_id}&filter=username&query={digits_phone}
```

Проверено в авторизованном браузере: параметр `query` с номером из цифр автоматически фильтрует список. Нативная карточка клиента открывается отдельным действием пользователя. `client_id` в ссылке списка не выполняет прямого перехода к карточке.

### YCLIENTS

```text
https://yclients.ru/clients/{external_company_id}/base?filters%5B0%5D%5Boperation%5D=OR&filters%5B1%5D%5Btype%5D=quick_search&filters%5B1%5D%5Bstate%5D%5Bvalue%5D={digits_phone}
```

Проверено в авторизованном браузере: **именно этот трёхпараметрический вариант** автоматически применяет поиск, включая телефон в формате только цифр. Сокращённый двухпараметрический вариант подставлял телефон, но требовал ручного «Найти». Не сокращать URL без отдельного регрессионного теста.

### Общие требования к генератору

- Использовать один централизованный builder, покрытый тестами; никаких склеек URL в разных компонентах.
- `digits_phone` формируется удалением `+`, пробелов, дефисов, скобок и остальных нецифровых символов; исходный номер в `Contact` не менять. Не угадывать отсутствующий код страны и не выполнять непроверенные преобразования вроде `8` → `7`.
- Если номер отсутствует или не является пригодным для поиска телефонным значением, **не показывать активную ссылку**. Валидация должна отбрасывать заведомо непригодные значения, не искажая корректные международные номера.
- Внешний `company_id` валидировать при сохранении конфигурации (ожидается цифровой ID); не принимать произвольные URL/домены от администратора.
- Без передачи API-токенов, персональных данных кроме телефонного поиска и дополнительных параметров. Ссылки открывать через `target="_blank"`, `rel="noopener noreferrer"`.
- Ссылка ведёт в интерфейс CRM; доступ определяется **штатной авторизацией самой CRM**. Не утверждать, что ссылка выдаёт права или что клиент в CRM существует.
- Подтверждённые вручную тестовые значения: DKD `company=515337` и телефон `79803565758`; YC `company_id=688638` и телефон `79162545243`. Эти значения **только для документации/ручной проверки**, не хардкодить в продукте и тестовой базе.

## 3. Архитектурные границы v1

Создать отдельное Django-приложение, условное имя `chatballs.crm_bridge`, со **собственными** моделями и миграциями. Названия классов ниже предлагаемые: агент вправе уточнить их по существующим соглашениям, сохранив поведение.

Минимальная логическая модель:

1. **`CRMOrganizationConfig`**: одна запись на `Organization`; поле `provider` = `NONE|YCLIENTS|DIKIDI`. При отсутствии записи поведение равно `NONE`.
2. **`CRMCompany`**: `organization`, человекочитаемое имя, `external_company_id`, `is_primary`, `is_active`. Один активный основной CRM-company в организации; уникальная пара `(organization, external_company_id)`. Основной внешний ID **показывается и редактируется прямо в «Настройки → Организация»**. Не дублировать этот ID вторым независимым полем в `identity.Organization`.
3. **`CRMConnectionBinding`**: связь `Integration` (мессенджер-подключение) с `CRMCompany`. Одно подключение указывает максимум на одну CRM-компанию. `Integration`, `CRMCompany` и `Organization` должны принадлежать одному tenant. Привязки обязательны для неоднозначных многозаводских/многофилиальных сценариев, но не блокируют конфигурацию одной компании.

В v1 **не создавать** `CRMProfile`, `CRMContactLink`, фоновые воркеры синхронизации и таблицы истории CRM. Эти сущности появятся только тогда, когда начнём получать данные YC/DIKIDI по API.

Будущее расширение: отдельные внешние CRM-профили с устойчивым ключом `(CRMCompany, external_client_id)`, снимками полей источника, синхронизацией и *явной* связью с `Contact`. Не добавлять «все поля CRM» в upstream `Contact`. Телефон предназначен для поиска/подбора кандидатов, но не является гарантией уникальности человека и не должен автоматически объединять контакты.

### Настройки и выбор CRM-компании

- `NONE`: CRM-ссылки отсутствуют.
- `YCLIENTS` или `DIKIDI` плюс основной `external_company_id`: обычный сценарий одной компании.
- Дополнительные `CRMCompany` и `CRMConnectionBinding`: несколько филиалов одной CRM.
- При наличии **ровно одной** активной CRM-компании можно использовать её как однозначный fallback для не привязанного подключения.
- При наличии нескольких активных компаний **нельзя молча угадывать филиал по основному ID**, если привязка подключения отсутствует: не строить потенциально неверную ссылку, показать понятное конфигурационное состояние в UI, где оно согласовано.
- Изменение провайдера или отключение CRM не должно тихо переинтерпретировать старые внешние ID под другой провайдер либо стирать привязки. Транзакционно определить и протестировать безопасный процесс смены/отключения с сохранением данных либо явным отказом до разрешения несовместимых привязок.

## 4. Контракт выбора ссылки в карточке

Ссылки должны быть контекстными, а не просто «телефон + случайный ID компании».

**Карточка контакта в диалоге:** выбрать CRM-компанию по `Conversation.connection_id` → `CRMConnectionBinding`; если привязки нет, применять правило однозначного fallback из §3. Телефон брать из доступного штатного `Contact.phone`. Не выводить ссылку, когда нет корректного телефона или выбора CRM-компании.

**Общая карточка клиента в «Контактах»:** у одного `Contact` могут быть диалоги через несколько подключений/филиалов. Если все доступные привязки дают одну CRM-компанию, показать одну ссылку. Если CRM-компаний несколько, предоставить явный выбор филиала/несколько подписанных ссылок после утверждения UI. Не делать «основной филиал» неявной заменой для неоднозначного контакта.

Не выводить потенциально чужие branch-ID или внешние ссылки пользователю, которому недоступен исходный контакт/диалог. В v1 не искать CRM-клиента по серверному API и не создавать `Contact` при открытии ссылки.

## 5. Backend и безопасность

- Включить `crm_bridge` в `INSTALLED_APPS` через минимальную правку `apps/backend/chatballs_backend/settings_base.py`.
- Добавить **одну тонкую точку маршрутизации** в существующий tenant-scoped URL-конфиг: предпочтительно `apps/backend/chatballs/identity/company_urls.py` → `company/crm/`, дальше собственный `crm_bridge/urls.py`.
- Предусмотреть tenant-scoped операции чтения/изменения конфигурации, списка компаний и привязок. Полномочия: чтение настроек по существующему `settings.view`, изменение по `settings.manage`; не создавать собственную систему ролей.
- Для чтения ссылок к контакту/диалогу использовать существующие селекторы видимости и соответствующие capabilities (например, `customers.view`, `conversations.view`). Простого совпадения `organization_id` недостаточно, если штатные правила ограничивают видимость конкретных диалогов.
- Поддержать отдельные read-only операции для контекста диалога и общей клиентской карточки, **не расширяя обязательные upstream API payloads**, если можно обойтись отдельным endpoint и маленьким компонентом.
- Все операции строго внутри штатного `request.tenant_context`, без tenant IDs, получаемых от браузера в качестве авторитетных.
- Свои таблицы должны иметь `organization_id`, надлежащие `UniqueConstraint`, tenant FK-проверки, RLS, PostgreSQL runtime grants и права `chatballs_schema` согласно существующему стеку. Применить модель `TenantRelationModel` где уместно и обеспечить ограничения также на уровне PostgreSQL, поскольку `bulk_update` и прямые SQL-записи могут обходить `save()`.
- **Миграции RLS и ограничений хранить внутри `crm_bridge/migrations/`**; не добавлять новые `00xx_...` в `identity`, `integrations` и `tenancy`.
- Не переименовывать, не сбрасывать и не переписывать существующие миграции. Выбирать точные межприложенческие dependencies на реально требуемые базовые модели и SQL-функции, проверять объединённый граф Django.
- Аудировать административные изменения CRM-настроек/привязок через штатный audit, не записывая лишние персональные данные или пользовательские URL.
- Никаких provider credentials, токенов, фоновых сетевых запросов и прямых SQL-импортов в v1.

## 6. Frontend: тонкая интеграция, без собственного параллельного UI

Проверенные в ветке потенциальные точки входа:

- `apps/internal-ui/src/features/administration/OrganizationSettingsForm.tsx` и `apps/internal-ui/src/features/settings/SettingsPage.tsx`: «Настройки → Организация». Здесь владелец видит поставщика CRM и **основной внешний ID компании**, а управление филиалами/связями с подключениями должно использовать согласованный UI.
- `apps/internal-ui/src/features/sales/dialogs/context/ClientContext.tsx`: карточка клиента рядом с диалогом.
- `apps/internal-ui/src/features/sales/client-detail/SalesClientHeader.tsx`: общая карточка клиента.
- `apps/internal-ui/src/api/client.ts`: автоматическая подстановка UUID активной организации реализована только для известных пространств имён. Поэтому API-запросы удобно размещать внутри уже зарегистрированного `/api/v1/company/...`, **не добавляя новый top-level namespace без причины**.

Создать переиспользуемый компонент условно `CrmProfileLink` с отдельным API client/хуком. В upstream-компонентах оставлять только небольшую вставку, не переписывать разметку карточек и не копировать большие компоненты.

**UI gate:** строго соблюдать корневой `AGENTS.md`. В частности, в продукт нельзя добавлять новые элементы/тексты/раскладки вне согласованного `design/baseline/<feature>/*.dc.html`. До реализации UI подготовить и согласовать соответствующий baseline; при отсутствии макета агент может реализовать и протестировать независимый backend, но должен остановиться перед внедрением нового видимого UI и явно сообщить о блокере. Использовать `shared/links.css`, штатные кнопки/формы, существующие стили. Все отображаемые строки через ru/en i18n.

## 7. Тесты и критерии приёмки

### Backend (только целевые тесты)

1. Provider `NONE` и отсутствие конфигурации: нет CRM-ссылок, старый Chatballs работает без изменений.
2. Одна организация, одна компания YC/DKD: верный URL и автоматическая фильтрация по нормализованному номеру, что соответствует подтверждённым browser smoke.
3. Форматы `+7 916 254-52-43`, `79162545243`: один корректный query `79162545243`. Непригодные номера не формируют ссылку.
4. YC URL сохраняет `filters[0][operation]=OR` плюс два параметра `quick_search`; DKD URL сохраняет `filter=username` + `query`.
5. Несколько филиалов, разные `Integration`: для каждого диалога выбирается его компания; общий контакт с несколькими компаниями не выдаёт ложную «единственную» ссылку.
6. Несколько филиалов, нет binding: отсутствует неоднозначный fallback.
7. Попытки создать cross-tenant `CRMConnectionBinding` отвергаются на уровне сервиса **и БД**; чтение чужих данных возвращает отказ/отсутствие, не утечку.
8. Несанкционированные GET/PATCH/DELETE: права `settings.view/manage`, `customers.view` и `conversations.view` реально применяются; ограничения видимости разговоров не обходятся.
9. Повторные сохранения, дубли внешних ID и конкурирующие назначения primary/binding обрабатываются предсказуемо.
10. Безопасная смена/отключение CRM не приводит к скрытой потере или неверной переинтерпретации данных.
11. Тестировать `migrate --plan`, `makemigrations --check --dry-run`, tenant RLS и миграцию на существующей БД в disposable окружении; документировать dependencies и порядок схемных миграций.
12. Регрессионно убедиться, что существующие пути редактирования/объединения контактов, Native Mirror, Gateway и обычные мессенджеры не изменены.

### Frontend после утверждения макета

1. Выбор CRM и основной внешний ID видны в «Настройки → Организация»; при `NONE` лишние поля не навязываются.
2. «Профиль YCLIENTS / DIKIDI» выводится только при определённой CRM-компании и пригодном телефоне.
3. Ссылка открывается в новой вкладке; компонент корректно переживает переключение организации/диалога без устаревшей ссылки.
4. При нескольких компаниях пользователь различает филиалы; UI не угадывает филиал.
5. Роли, мобильная верстка, ru/en i18n, ошибки сети и штатные состояния не регрессируют.

### Definition of Done

- Изолированные `crm_bridge` модели, API, URL builder, тесты и собственные миграции.
- Минимальный, документированный набор upstream touchpoints; отдельно отметить риск их изменения при релизах upstream.
- Нет изменений схемы `identity.Organization`, `conversations.Contact` и `integrations.Integration`.
- Нет массового импорта клиентов, CRM API и синхронизаторов.
- Целевые тесты и lint/typecheck для реально затронутых файлов; **не запускать полный тестовый набор без отдельной команды владельца**.
- Schema-change test DB пересоздавать только когда необходимо; следовать `AGENTS.md`.
- Никаких production-миграций/деплоя без отдельного согласования владельца.
- Один осмысленный коммит/серия логичных коммитов после согласованных этапов; не смешивать с upstream update и изменениями Native Mirror.

## 9. Что сознательно НЕ входит в v1

- API-интеграции с YC / DIKIDI, OAuth/токены, чтение списков клиентов и синхронизация.
- `CRMProfile`/`CRMContactLink`, маппинг CRM client ID, загрузка истории посещений, абонементов, покупок, расширенных атрибутов.
- Автоматическое слияние контактов по телефонному совпадению.
- Прямая навигация в карточку CRM по клиентскому ID, которая пока не подтверждена.
- Массовый импорт клиентов в upstream `Contact` (тем более что штатный список `clients_queryset` скрывает контакты без видимых диалогов).
- Переустройство штатной карточки Chatballs, новый общий дизайн-системный слой либо замена мессенджерного runtime.
