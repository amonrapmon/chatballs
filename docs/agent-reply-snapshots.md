# Финальный ответ и снимок доставки

Контракт T-161, ADR-0036, SPEC-0035 R-5–R-10, R-17–R-23.

## Ход

План одним запросом копирует подключённые навыки, их инструкции, шаблоны и
ревизии. Содержимое шаблонов хранится в неизменяемых JSON-строках только в памяти.
Начальный каталог по-прежнему содержит только id/name/description.
Внутренняя загрузка возвращает instruction и, при наличии шаблонов, templates
с полями id/name/purpose/schema. HTML, CSS и редакторские примеры модели не передаются.
Загрузка без шаблонов сохраняет прежний контракт.

При наличии шаблонов предлагается внутренняя операция chatballs_prepare_reply:

```json
{"skill_id":"<UUID из каталога>","template_id":"<UUID из загруженного навыка>","data":{}}
```

Имя получает свободный суффикс при конфликте с внешним инструментом.
Доступен только шаблон успешно загруженного навыка из плана текущего хода.
Загрузка не расширяет права внешних инструментов.

До рендера сервер проверяет размер/вложенность данных, восстанавливает известные
токены в значениях и ключах, затем проверяет типы, обязательность и неизвестные поля.
Числовой токен целиком может восстановить JSON-число; обычные строковые числа
не приводятся к числу. Неизвестный/повреждённый токен отклоняет подготовку,
включая необязательные поля. После восстановления работает общий render_template:
проверка схемы, контекстное экранирование, положительная HTML/CSS-политика и
окончательная очистка. Готовый HTML никогда не проходит повторное восстановление.

Операция возвращает только final_response — непрозрачную строку
CHATBALLS_PREPARED:<случайный идентификатор>. Это ссылка только внутри текущего
хода; она не содержит данных и не требует отдельной клиентской сущности.
Модель завершает ход этой строкой целиком либо обычным текстом. Для передачи
человеку к ссылке добавляется штатный <<HANDOFF>>. Неизвестная ссылка и смесь
ссылки с текстом завершаются безопасным отказом; подготовка сама ничего не отправляет.
Несколько подготовок не создают серию сообщений: сохраняется только выбранная.
Все операции входят в общий бюджет 5 раундов с заключительным ответом, 20 операций,
16 KiB аргументов операции и 512 KiB результатов; отдельного цикла коррекции нет.

## Message

Оформленный ответ сохраняется один раз:

| Поле | Значение |
| --- | --- |
| text | Готовый клиентский текст |
| content_html | Очищенный HTML того же набора данных |
| format_version | 1; старые сообщения остаются 0 |
| presentation | formatVersion, css, isolation=sandboxed-iframe, sandbox="", srcDoc |
| delivery_representation | html для WEB; text для Telegram/MAX/VK/email |
| template_snapshot | id и name шаблона, skillId и skillRevision на момент планирования |
| ai_reply_to | Уникальная связь с входящим сообщением для повторов события |
| ai_delivery | Закрытый маршрут транспорта и подтверждение успешной доставки |

Живой ссылки на навык или шаблон нет. Изменение, отключение или удаление
конфигурации не меняет текст, HTML/CSS, подписи и выбранное представление.
Отдельный JSON рендер-данных и карта восстановления не сохраняются.
В диагностике ходов с шаблонами аргументы операций и результаты инструментов
исключены до редактирования/сохранения. Учёт обращений и токенов всех раундов сохраняется.
История AI берёт только text и маскирует его новой картой следующего хода.

## Доставка и чтение

Перед фиксацией заново блокируются строки диалога и входящего сообщения:
перехват, отмена и отключение агента отменяют ответ; срок хода переводит его
в штатный сценарий недоступности AI. Доменные события PUBLIC_REPLY и QUEUE_ENTERED,
передача человеку и уведомления продолжают прежний жизненный цикл.

Маршрут берётся из фактического входящего письма EmailThreadMessage, если оно
существует. Поэтому почтовое продолжение веб-диалога получает текст через SMTP,
с сохранёнными Message-ID/References и почтовым подключением, хотя источник
Conversation остаётся WEB. Обычные мессенджеры используют штатный send_reply;
обычная почта — существующий построитель письма/SMTP. Сеть выполняется вне транзакции.

Повтор исходного outbox-события находит ai_reply_to и отправляет сохранённый text
по сохранённому маршруту; повторного вызова модели/рендера/логического ответа нет.
Подтверждённая отправка повторно не выполняется. Как и у существующих транспортов,
сбой процесса между приёмом внешним сервером и записью подтверждения может привести
к повтору внешней отправки; гарантии exactly-once у SMTP/мессенджеров не добавляются.

Внутренний message_payload, включая REST-обновление после WebSocket-инвалидации,
возвращает formatVersion/contentHtml/presentation/deliveryRepresentation/template.
Сокет по-прежнему передаёт только уведомление conversation.changed, без содержимого.
Проверочный чат возвращает те же поля рядом с reply и использует общий runtime;
клиентские контакты, диалоги, сообщения и outbox им не создаются.

Публичная история добавляет снимок только для исходящего AI формата 1,
доставленного как html. Обычный HTML входящей почты и старые сообщения
сохраняют прежнюю семантику. Публичная сессия ограничена её организацией,
подключением, каналом, контактом и выбранным открытым диалогом; внутренние
события и конфигурация навыка не выдаются.

Тип MessagePresentation опубликован в @chatballs/contracts и подключён к типам
внутренних сообщений, проверочного чата и виджета. UI отображения входит в
следующие задачи этапа: потребитель srcDoc обязан использовать iframe с пустым
sandbox, без allow-scripts/allow-same-origin и с referrerPolicy=no-referrer.
В этой задаче продуктовые экраны и дизайн не меняются.
