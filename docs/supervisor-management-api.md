# Назначение супервизора и подконтрольных групп

Роль `SUPERVISOR` — фиксированная роль membership организации (ADR-0033).
`EmployeeGroupSupervision` хранит область контроля отдельно от обычного
членства `EmployeeGroupMember`. Новая роль не назначается миграцией автоматически.

## Управление существующим сотрудником

`POST /api/v1/organizations/{organization_public_id}/employees/{user_id}/update/`

Доступ: активные OWNER/ADMIN текущей организации. Супервизор не может менять
свои полномочия или полномочия коллег. Владелец сохраняет существующую защиту
от смены роли: для этого используется передача владения.

Тело существующего обновления карточки:

```json
{
  "fullName": "Имя сотрудника",
  "email": "employee@example.org",
  "role": "SUPERVISOR",
  "supervisedGroupIds": [12, 17]
}
```

`supervisedGroupIds` заменяет весь набор подконтрольных групп. Повторяющиеся
идентификаторы объединяются. Поле можно опустить, чтобы сохранить область;
`[]` отзывает её полностью. `null`, неверные типы, отсутствующие и чужие группы
возвращают 400 без частичных изменений. Непустая область допустима только
для `SUPERVISOR`. Снятие роли очищает область, сохраняя обычное членство в группах.

Ответ обновления, карточка и список сотрудников содержат `supervisedGroups`:
массив объектов `{"id": 12, "name": "Поддержка"}`. Флаг
`permissions.canChangeSupervisedGroups` описывает доступность изменения.
Эффективный доступ сессии также содержит `supervisedGroups`; для заблокированной
membership он пуст. Поле `groups` по-прежнему означает обычное членство.

Создание сотрудника и приглашение поддерживают новую роль; начальная область
пустая и назначается после появления membership через обновление карточки.

## Аудит и изоляция

`identity.employee_role_changed` хранит `oldRole` и `role`;
`identity.employee_supervised_groups_changed` — `oldGroupIds` и `groupIds`.
Инициатор, время, организация и сотрудник записываются штатным аудитом.
Payload содержит только роли и идентификаторы групп. Повторное сохранение
неизменной области не создаёт событие изменения области.

Удаление подконтрольной группы и передача владения также отзывают область
с аудитом. На новой таблице действуют FORCE RLS и tenant-триггеры для обеих
связей; bulk INSERT/UPDATE не обходят проверки организации.

Эта реализация добавляет хранение и администрирование области. Управленческие
операции над диалогами и отчётами реализуются следующими серверными задачами;
здесь SUPERVISOR получает базовые возможности EMPLOYEE без административного
доступа. UI назначения в этой задаче не добавляется.
