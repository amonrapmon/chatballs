# Хранение внутренних комментариев

`ConversationComment` — отдельная последовательная история организации и
диалога. Запись содержит обязательного автора из этой организации, текст,
серверное `created_at`, явно указанную аудиторию `INTERNAL` и `operation_id`.
Автор защищён от удаления через `PROTECT`. Уникальная пара
`organization / operation_id` не позволяет сохранить повтор операции.
Обработку повторного запроса и ограничения длины текста задаёт
[API комментариев](internal-comments-api.md).

Существующая `Conversation.note` остаётся отдельной изменяемой заметкой.
Миграция не создаёт комментарии из заметок и не изменяет таблицу `Message`.
API и realtime работают с этой отдельной историей; нового UI нет.

`history_selectors.conversation_records(conversation, audience=...)` выбирает
`Message` для `PUBLIC` и `ConversationComment` для `INTERNAL`. Вызывающий код
сначала проверяет доступ к диалогу через существующие tenant-сервисы, затем
применяет курсор и лимит к выбранному queryset. `conversation_messages`
сохраняет прежний публичный контракт. Смешивать идентификаторы двух историй
в одном курсоре нельзя: это независимые таблицы и последовательности.

Для обеих историй используется существующее окно `api.pagination.window`
с ключами `created_at / id` в нужном направлении. Индекс комментариев имеет
префикс `organization / conversation / audience`, затем `created_at / id`;
одинаковое время разрешается уникальным `id`.

Таблица комментариев защищена принудительным RLS и constraint triggers
для диалога и автора. Runtime-роль может только читать и добавлять записи;
обновление и удаление ей запрещены. Модель также запрещает повторное сохранение
отправленного комментария. Сервис создания и защищённый API проверяют
действующие права и сопоставляют содержимое идемпотентного повтора.
