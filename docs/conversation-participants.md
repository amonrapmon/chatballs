# Совместная работа участников диалога

Серверная часть SPEC-0026 не требует нового интерфейса. Единственный
ответственный сохраняется при добавлении, удалении и ответе участника.
Начальный лимит организации — 5 дополнительных активных участников;
ответственный в него не входит. Уменьшение лимита сохраняет текущий состав,
но запрещает новые подключения сверх лимита.

Маршруты ниже находятся под
`/api/v1/organizations/{organization_public_id}/conversations/`.

| Метод и путь | Назначение |
|---|---|
| `GET participant-limit/` | Текущий лимит, по праву чтения диалогов |
| `PATCH participant-limit/` | Только OWNER/ADMIN; `additionalParticipantLimit`: целое число от 1 до 10 |
| `GET {id}/participants/` | Активный состав, по праву чтения диалога |
| `POST {id}/participants/` | `membershipId`, обязательная непустая `reason` |
| `DELETE {id}/participants/{participantId}/` | Завершение участия с обязательной `reason` в JSON |
| `GET {id}/participants/history/` | Журнал по праву чтения, `page`, `pageSize` |
| `GET {id}/participation-journal/` | Общий журнал; `kind=all/participants/transfers`, `page`, `pageSize` |

Управлять составом могут назначенный сотрудник, OWNER/ADMIN и супервизор
в своей области контроля. Чтение по группе или участие сами по себе такого
права не дают. Цель добавления — действующая неблокированная membership той
же организации с активной учётной записью.

Повторное добавление активного участника возвращает прежнюю запись (HTTP 200;
новая запись — 201), сохраняя исходные причину, инициатора и время.
Повторное удаление возвращает завершённую запись. Удаление адресует конкретный
эпизод участия: повтор старого DELETE не завершает новое подключение сотрудника.
HTTP API не позволяет редактировать или удалять журнал.

Участие даёт чтение истории, действующую внутреннюю заметку и клиентский ответ
в режиме HUMAN. Внутренние комментарии используют то же право и остаются
отдельной от публичных сообщений историей; отдельная заметка сохраняет прежнее
поведение. Текст, файлы, голосовые и AI-черновики используют согласованные права
ответа. Автор сообщения — отправивший сотрудник.
Участие само по себе не даёт права перехвата, смены ответственного, переноса,
звонка или завершения диалога.

Проверка лимита и изменение состава выполняются в одной транзакции под
блокировкой организации и диалога. Проверка ответа и удаление участника
используют ту же блокировку диалога. Следующий запрос после удаления проверяет
текущие права; независимые основания доступа по группе, назначению и управлению
сохраняются. Открытый WebSocket повторно проверяет права на каждую доставку.
Повторы штатных операций с `Idempotency-Key` также перепроверяют права до
возврата сохранённого результата. Ответ участника создаёт PUBLIC_REPLY с его
авторством и прежним ответственным, без ACCEPTED и переназначения.
Событие состава публикуется после commit; идентификатор диалога получает только
сотрудник с доступом после операции. Общее `inbox.changed` не содержит данных
диалога и позволяет обновить список после утраты доступа.

Внутренние причины и журнал не сохраняются в публичной ленте, AI-истории или
payload realtime. Добавление создаёт отдельное системное событие с кодом
`specialist_joined` и именем специалиста. Согласованный владельцем текст:
«К диалогу подключился специалист {имя}.» Английский перевод:
«Specialist {name} has joined the conversation.» Текст собирается через i18n
на языке организации; в БД хранится код и параметры, без готовой фразы.
Веб-виджет получает уведомление штатной историей, мессенджеры — через
transactional outbox и штатный `send_reply`. Повтор добавления не создаёт
нового события; завершение и повторная обработка успешно доставленного события
не создают повторного уведомления. При сбое действует штатный retry outbox.
Как у обычной отправки, сбой процесса между внешней отправкой и фиксацией
результата может привести к повторной доставке во внешнем транспорте.


## Дополнение API для T-105

Владелец согласовал диапазон API 1–10 по макету N1–N2. Схема БД
и уже сохранённые значения не переписываются: GET возвращает фактическое
значение, следующие изменения через API принимают только 1–10.
Ответ лимита включает `updatedAt` и `updatedBy` последнего сохранения через API;
до первого сохранения это `null` и пустая строка. Сохранение записывается в аудит.
PATCH лимита и добавление участника используют одну блокировку организации.

Справочник `GET directory/` возвращает `membershipId` вместе с прежним `id`
пользователя. Состав и журнал дополняются объектами `member`, `joinedBy`,
`leftBy` (`membershipId`, `userId`, `name`, `avatarUrl`); `leftBy` равен `null`
до завершения участия. Имена доступны и для завершённых эпизодов с заблокированным
участником, по прежнему праву чтения диалога. Ответ состава также содержит
`additionalParticipantLimit`. Внутренние причины и эти объекты не попадают
в публичную историю.

Публичная история WEB содержит `authorName` для ответа сотрудника (только имя,
без подстановки служебного email) и `systemEvent: "specialist_joined"` для
согласованного уведомления. Для других сообщений `systemEvent` пуст.
Код используется для оформления; в тексте клиент его не видит.

Состав дополнен фактическими `workStatus`, `online`, `lastSeen` из общего API
доступности сотрудников. Подробная карточка возвращает `access.isParticipant`,
`canReply` и `canControl`, список — `isParticipant` для текущего сотрудника.
После утраты доступа detail сохраняет HTTP 404 и для собственного завершённого
эпизода возвращает только `participationEndedBy`, без причины или истории.
У постороннего сотрудника или другой организации этого поля нет. Имя контакта
для экрана утраты доступа берётся только из уже прочитанной карточки браузера.
