# Журнал доменных событий обращения

`ConversationEvent` хранит факты поддержки в существующей PostgreSQL:
принятие, назначение, передачу, вход/выход очереди, публичный ответ,
закрытие и последующее обращение. Назначение и принятие — разные типы.
`actor_kind` отличает сотрудника, AI, клиента и систему.

Это основа данных B14.1 (SPEC-0030 R-1, R-9, R-10, ADR-0034).
Запись из штатных переходов подключается отдельно в B14.2; расчёты,
API полноты истории и экспорты — в последующих задачах. Новый UI не добавлен.

## Запись и повтор операции

Сервис записывает изменение домена и все его факты в одной `tenant_atomic`
транзакции с проверенным tenant-контекстом. Триггер INSERT блокирует строку
диалога, назначает следующую положительную последовательность внутри диалога
и серверное время `clock_timestamp()`. Переданное вызывающим кодом время
или последовательность заменяется БД. При обычном INSERT без явных значений
Django получает оба поля через RETURNING; после явного задания полей следует
вызвать `refresh_from_db()`.

Ключ уникальности — `(organization, operation_id, event_type)`: одна операция
может одновременно создать, например, принятие и выход из очереди, но ретрай
не создаст второй факт того же типа. `operation_id` обязан оставаться тем же
при повторе логической операции; генерация нового UUID на каждом ретрае
не обеспечивает идемпотентность. Обработка конфликта ключа и проверка
соответствия исходной операции относятся к вызывающему сервису.

## Исторические измерения и изоляция

Инициатор и ответственный — идентификаторы глобальных пользователей,
проверенные по membership организации. Группа и фактическое подключение —
идентификаторы соответствующих объектов; транспорт — код провайдера
подключения-мессенджера. При отсутствии подключения транспорт тоже `null`:
скрытый `Channel` не используется как его замена.

Измерения сохраняются как числовые снимки: модель и PostgreSQL проверяют
при вставке их принадлежность организации. Они не имеют FK к изменяемым
измерениям, поэтому удаление membership, группы или подключения не стирает
историческую атрибуцию. UPDATE фактов запрещён триггером, в том числе для
schema-роли. Текущие измерения диалога не переписывают уже сохранённые факты.

Связь с самим диалогом — FK с Django CASCADE. Штатное физическое удаление
диалога удаляет его факты; SQL DELETE родителя без удаления зависимостей
защищён FK. Runtime app имеет SELECT/INSERT/DELETE под forced RLS, без
tenant-контекста доступ закрыт. Platform-роль доступа к журналу не получает.
Исторические измерения не являются основанием авторизации будущих отчётов:
доступ должен ограничиваться текущим разрешённым набором диалогов.

В журнале нет текста, имён, комментариев, JSON payload, секретов, аргументов
или результатов инструментов. Типы фактов, инициаторов и транспорта
ограничены кодами на уровне БД.

## Доступность истории

Миграция создаёт пустой журнал и единственную запись
`ConversationEventHistoryStart(pk=1).available_from` с серверным временем
включения хранилища. Повтор обычного migrate эту дату не изменяет.
Это общая для установки техническая граница без tenant-данных; app может
только читать её. Новые организации используют ту же нижнюю границу.

Прежние сообщения, назначения, передачи и статусы не превращаются в факты.
Граница означает доступность хранилища, а не полноту всех источников:
подключение источников B14.2 и обращения, начавшиеся до границы, необходимо
учитывать при расчёте полноты. Отсутствующие интервалы нельзя восстанавливать
из текущего состояния или считать нулевыми.
