# Оценки клиентов и качество в отчёте поддержки

Реализация T-141 использует исходный
`design/baseline/platform-expansion/Статистика и качество.dc.html`, ST4–ST5.
Макет и служебные документы Skaro не изменяются. Структура вкладок, блоки шкал,
таблицы сотрудников и критериев, подписи и распределение сохраняются.

Владелец в чате T-141 согласовал расширение штатного API и его реализацию
перед UI. Это расширение включает явное отсутствие оценки как исключение
из прежнего требования SPEC-0033 R-5 о значении допустимой шкалы.

## Контракт и расчёт

Существующие `customerRatings` и `qualityAnalysis` в сводке и строках сотрудников
сохраняют `state`, `count`, `groups`, `details`, период и политику ревизий.
Расчёт выполняется внутри `calculate_support_report`; фронтенд не агрегирует
баллы, не складывает сотрудников и не пересчитывает содержимое экспортов.

`customerRatings.scaleSummaries` разделяет точные снимки шкалы через тот же
`scaleId`, что исходные распределения. Подписи входят в идентичность снимка.
Каждый блок содержит `scale`, `ratingCount`, `meanValue`, `commentCount`,
`distribution` (value, label, count, rate) и `delivery`.

- Полученные оценки используют `received_at ∈ [from,to)`; среднее — сумма
  значений / число оценок только внутри этого снимка. Нет оценок — `null`.
- Доли распределения — count / ratingCount; при отсутствии оценок — `null`.
- `commentCount` учитывает непустые после удаления внешних пробелов комментарии.
- `delivery.sentCount` считает фактически отправленные запросы с
  `sent_at ∈ [from,to)`, а не запланированные или отменённые до отправки.
- `delivery.answeredCount` считает ответы на эти запросы, полученные раньше
  `answeredBefore = min(to, generatedAt)`. Доля — answeredCount / sentCount;
  нулевой знаменатель даёт `null`. Ответы на запросы до начала периода могут
  входить в ratingCount, но не в этот набор отправленных запросов.
- Основания периода явно возвращаются в `periodBasis` секции и delivery.
  Числа и снимки в таблицах сотрудников используют ту же формулу.

`qualityAnalysis.versions` содержит критерии каждой доступной версии, включая
версии без анализов в периоде. OWNER/ADMIN получают каталог своей организации;
SUPERVISOR — только версии, связанные с анализами текущих доступных диалогов,
в том числе вне периода. EMPLOYEE не получает ни каталог, ни сводки.

`validFrom` — created_at версии, выбранной настройкой при её создании;
`validTo` — создание следующей версии или null. Это период выбора набора,
а не обещание непрерывно включённого анализа. Даты форматируются в часовом
поясе отчёта; validTo исключающая. История включения отдельно не восстанавливается.

Сохраняется `latest_per_completion`: последняя ревизия каждого завершения;
WAITING/RUNNING/FAILED не заменяются прежними успешными баллами.
`analysisCount` считает только SUCCEEDED, `selectedJobCount` — выбранные работы
всех состояний. Качество отбирается по времени события завершения.

Строка критерия содержит name, description, scale, scoredCount, missingCount,
correctedCount, originalSummary и effectiveSummary.

- Числовые шкалы: kind=mean, арифметическое среднее известных баллов.
- Строковая бинарная шкала: kind=positiveRate, доля явно указанного positiveValue
  среди известных баллов. Автоматического толкования «Да», Yes или порядка нет.
- Иные строковые шкалы: kind=unavailable, value=null.
- Среднее никогда не объединяет версии и коды критериев.
- correctedCount — число заключений с корректировкой, не число её ревизий;
  возврат к исходному значению тоже является корректировкой.
- correctedAnalysisCount и correctionRate считают успешные анализы с хотя бы
  одной корректировкой / все успешные анализы версии.
- Нет успешных анализов — analysisCount=0, показатели строк null; нет известных
  баллов при успешном анализе — scoredCount=0, среднее null, missingCount известен.

Новые снимки критериев принимают необязательные `name` и
`reporting: {positiveValue}`. PositiveValue допускается только для бинарной
строковой шкалы и должен входить в неё. Старые снимки не переписываются:
name берётся из description, положительное значение не назначается.

## Явное отсутствие оценки

Полный вывод AI по критерию может содержать `value: null` и
`missingReason: "insufficient_messages"`. Объяснение обязательно; список
messageIds может быть пустым только в этом случае. Вывод всех критериев
по-прежнему обязателен; невалидный ответ, чужие сообщения и ошибки провайдера
не становятся успешными анализами без оценки.

Null исключается из среднего и учитывается в missingCount. Корректировка
может заменить его допустимым баллом; исходное значение остаётся null.
Промпт и проверка результата продолжают использовать общий слой псевдонимизации.

## Экспорт и интерфейс

CSV/XLSX дополнены таблицами rating_summaries, rating_distribution,
quality_summaries: экспортируется готовый серверный расчёт, включая исходные
и действующие значения, доли и даты. Числа в XLSX остаются числами, строки
проходят существующую защиту от формул; ru/en содержат одинаковые ключи.

UI использует общие фильтры, таблицы, аватары и вкладки базового отчёта.
Сводки оцениваются независимо от полноты событийных длительностей.
Пустые наборы используют уже утверждённое состояние ST10; версии без анализов
используют блок ST5 с «—». Общий сбой использует ST12 и сохраняет фильтры.
Показатели не пересчитываются на фронтенде. Новые компоненты и модули
содержат отдельные обязанности, без копирования макета в один большой файл.

Проверка и оставшиеся ограничения описаны в `verification/T-141/README.md`.
