# Данные почтового продолжения веб-обращения

Реализованы модели данных SPEC-0031 R-1, R-2, R-7 и ADR-0035.
Миграции `conversations/0032` и `tenancy/0043` добавляют пустые таблицы;
исходные диалоги, сообщения, назначения и контакты не переписываются.

- `EmailThread` хранит исходный WEB-диалог, дополнительное EMAIL-подключение,
  нормализованный адрес и тему. При создании принимается только активное
  EMAIL-подключение той же организации и адрес из `Contact.email` либо
  существующей EMAIL-идентичности этого контакта. Совпадение email разных
  контактов не создаёт идентичность и не объединяет контакты.
- `EmailThreadMessage` связывает публичное сообщение с тредом и фактическим
  подключением, хранит направление, `mail_message_id`, `in_reply_to` и
  `references`. `message_id` — FK на сообщение Django, а `mail_message_id` —
  заголовок Message-ID письма. Последний уникален внутри почтового подключения.
  Сообщение обязано принадлежать диалогу треда, подключение — совпадать с ящиком
  треда.
- `EmailSendOperation` ссылается на исходящее письмо, хранит инициатора
  (членство организации), время и клиентский ключ, уникальный для организации.
- `EmailSendAttempt` хранит номер внутри операции, инициатора, время создания,
  начала и завершения, фактическое состояние и безопасный код ошибки. Каждая
  попытка связана с отдельным существующим tenant-событием штатного outbox.

Состояния попытки:

| Код | Смысл | Время |
| --- | --- | --- |
| `PENDING` | Ожидание обработки | Начало и завершение пусты |
| `SENDING` | Отправка началась | Есть начало, завершение пусто |
| `SMTP_ACCEPTED` | SMTP принял письмо | Есть начало и завершение |
| `FAILED` | Подтверждённая ошибка | Есть завершение; начало может отсутствовать при отказе до отправки |
| `UNKNOWN` | Исход отправки неизвестен | Есть начало и завершение |

Принятие SMTP не подтверждает доставку или прочтение. Отдельного состояния
доставки без достоверного события почтового контура нет. `FAILED` и `UNKNOWN`
требуют код ошибки; остальные состояния хранят пустой код. Разрешены только
`CONNECTION_UNAVAILABLE`, `SMTP_REJECTED`, `TRANSPORT_ERROR` и
`WORKER_INTERRUPTED`; сырого текста ошибки и секретов в журнале попыток нет.
Время проверяется на хронологический порядок.

Все четыре таблицы используют обязательный tenant-ключ, FORCE RLS и
существующие проверки tenant-FK. Runtime-доступ требует `tenant_atomic`;
роль platform не имеет прямого доступа к таблицам. Bulk-вставки и UPDATE
проверяются БД, включая соответствие сообщения треду и ящика выбранному
транспорту. Маршрут треда, идентификатор письма, связь операции и параметры
попытки неизменяемы; смена email контакта или отключение ящика сохраняет
исторический снимок. Исходный канал/агент, контакт, группа, ответственный и
WEB-подключение диалога остаются источником обращения.

Здесь нет HTTP API, обработчика SMTP/IMAP или нового UI. Модели задают форму
данных и ограничения; переходы между состояниями, авторизацию отправки,
разрешение ответов по заголовкам и проверку допустимости ручного повтора
выполняет использующий их сервис. Создание записи само по себе не отправляет
письмо и не запускает outbox-обработчик.

Проверки в штатном окружении задачи:

```powershell
docker compose build backend-admin
docker compose exec -T backend-admin python manage.py migrate --noinput
docker compose exec -T backend-admin python manage.py check
docker compose exec -T backend-admin python manage.py makemigrations --check --dry-run
docker compose exec -T backend-admin pytest -q chatballs/conversations/test_email_continuation_models.py chatballs/conversations/test_email_attempt_models.py chatballs/conversations/test_email_continuation_guards.py chatballs/conversations/test_email_continuation_migration.py --reuse-db
```

Тесты работают только в отдельной Django test-БД, с реальным PostgreSQL и его
runtime-ролью. При изменении схемы первый прогон использует `--create-db`;
последующие — только `--reuse-db`. Демо-данные и учётные записи рабочей базы
не изменяются, почтовые серверы и заглушки для проверки не запускаются.
