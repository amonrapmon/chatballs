# Настройки и передача диалога

Реализация T-093 использует штатный API назначения. Форма передаёт получателя,
активную причину, внутренний комментарий, версию назначения и UUID операции.
Повтор после сетевой ошибки с неизменной формой сохраняет UUID; изменение
формы создаёт новый UUID. При HTTP 409 форма перечитывает карточку, показывает
конфликт и не повторяет операцию. При HTTP 400 перечитываются получатели и
активные причины. Присутствие, рабочий статус и нагрузка показываются отдельно;
разрешение назначения берётся из `assignmentAllowed`.

Настройки доступны владельцу и администратору; сервер проверяет доступ к
справочнику и политике. В форме передачи используются `access.actions` текущего
диалога. Серверные ошибки показываются без локальной подмены правил.

## Дизайн и решения владельца

Источник — `design/baseline/platform-expansion/`: настройки N1–N2,
форма «Передача диалога», K3–K5, M2 и состояния P1–P6.

11.10.2026 владелец согласовал сохранение действующей политики API:
все четыре переключателя изменяемы. Блокировка «Готов» и пояснение о
невозможности отключить назначение из N1 не переносятся.
Начальные значения интерфейс не подставляет: они читаются с сервера.

Владелец согласовал текущую адаптацию N1–N2 для мобильных настроек
как исключение из отдельного кадра M. Сохраняются карточки причин и политики,
доступные действия создания, переименования и отключения причины;
изменения применяются сразу через штатный API. Отдельный мобильный список
с переходами в редактор и закреплённое «Сохранить» из M не используются.
Согласованный вариант зафиксирован в
[снимке мобильных настроек](verification/T-093/settings-mobile.png).

Владелец разрешил дополнить API счётчиком использований, сведениями о
переименовании и проверкой названия. Последнее переименование сохраняет
предыдущее название и фактическое время изменения; миграция не восстанавливает
несуществующую историю. Названия сравниваются без учёта регистра после обрезки
краевых пробелов; запись каталога сериализуется блокировкой организации.

Для общего журнала P6 с вкладками «Все», «Передачи», «Участники» владелец
сначала установил зависимость от штатного API участников, затем разрешил
продолжить работу. В ветку подключена реализация T-098 из коммитов
`7cd9c4c9` и `1dc7507c` с сохранением API передачи. Добавлен защищённый
`activity-history/` с общей серверной сортировкой и пагинацией.
При обновлении ветки подключены окончательно опубликованные T-098 и T-105,
T-092 и T-071 из `main` (`f4fa06a2`). Промежуточное слияние сохранено
коммитом `6414dc6b`. Права повторов операций используют окончательные guards
T-098; возможности супервизора, внутренние комментарии и библиотека шаблонов
сохраняются. В N1–N2 карточка лимита T-105 следует за причинами и политикой.
В контекст-панели остаётся один предпросмотр журнала T-105; его «Вся история»
открывает общий P6. Параллельный блок последних передач исключён, оба API
журналов сохранены для совместимости. Предпросмотр использует согласованные
нейтральные подписи. Экран утраты доступа и авторство участников из T-105
сохранены. Объединяющие миграции не изменяют данные или схему.
По «Вся история» открывается P6 в стандартном диалоге шириной 420 px
без дополнительных заголовков и кнопок. Закрытие — по Esc или клику вне.
Такое размещение явно согласовано владельцем. Вкладки фильтруются API,
следующие страницы подгружаются при прокрутке; при обновлении диалога
журнал перечитывает актуальное начало списка.
Согласованы нейтральные подписи «{Инициатор} → {Участник} · Подключение»,
«{Инициатор} → {Участник} · Завершение участия» и
«{Имя}: диалог взят из очереди». Подписи передач сохраняются прежними.

Снимки причины и комментарии читаются только из защищённой истории передач.
Их нет в клиентской переписке или контексте AI. История показывает названия
участников операции и пометки о текущем переименовании/отключении причины;
сам снимок операции и ответ идемпотентного повтора остаются неизменными.

Карточка уведомления K5 использует согласованную нейтральную подпись
«{Имя}: вам передали диалог». Обычное уведомление содержит только ссылку на
передачу и безопасный текст; отправитель, его аватар, название диалога,
причина и комментарий загружаются отдельным запросом защищённой истории.
При отсутствии доступа остаётся безопасное уведомление. Внешнее уведомление
не получает внутреннюю причину или комментарий.
Системное событие хранит только ссылку на передачу: подробная подпись K4
с именами и причиной также собирается из защищённой истории, а обычный текст
сообщения остаётся безопасным.
Владелец также согласовал нейтральные подписи K4 «Диалог передан: {Имя}»
и «{Отправитель} → {Получатель} · {Причина}»: API не предоставляет падежных
форм имён и пола сотрудников.
Для широкой мобильной кнопки M2 согласовано «Передать: {Имя}».
Для владельца и администратора согласовано пояснение K3
«Ответственным станет {Имя}»: действующий API сохраняет им право отвечать
после передачи. Для остальных сотрудников сохраняется предупреждение
из макета. Роль выбирает только текст; доступность действия и ошибки
по-прежнему определяет штатный API.

## Проверки

Штатное окружение задачи запускается через Skaro с `backend-admin`, базой,
кешем, приложением, фронтендом и воркерами. Сборка:

```powershell
docker compose exec -T frontend npm --workspace @chatballs/internal-ui run build
```

Для браузерной проверки собранного пакета штатный Vite обслуживает
`/dist/index.html` в том же frontend-сервисе. Использован вариант сборки
`docker compose exec -T frontend npm --workspace @chatballs/internal-ui run build -- --base=/dist/`.
Он меняет только префикс ссылок на собранные файлы; запросы остаются
в штатном прокси к backend этой задачи. Дополнительный сервер не запускается.

Только затронутые серверные сценарии:

```powershell
docker compose exec -T backend-admin python -m pytest -q --reuse-db chatballs/conversations/test_transfer_reasons.py chatballs/conversations/test_transfer_reason_display.py chatballs/conversations/test_transfer_journal.py chatballs/conversations/test_transfer_api.py chatballs/conversations/test_transfer_access.py chatballs/conversations/test_assignment_policy.py chatballs/i18n/tests.py
```

Первый прогон после изменения схемы дополнительно использует `--create-db`;
повторные проверки используют существующую тестовую базу. Полный набор не
запускается. Браузерная проверка использует установленный демо-набор из копии
основной базы и существующие учётные записи; seed и изменение доступов не нужны.

После добавления связи карточки уведомления отдельно выполнены 24 теста:

```powershell
docker compose exec -T backend-admin python -m pytest -q --reuse-db chatballs/conversations/test_transfer_api.py chatballs/conversations/test_transfer_access.py chatballs/conversations/test_transfer_reason_display.py chatballs/notifications/tests.py::DeliveryTests
```

После согласования пояснения OWNER/ADMIN проверены только связанные
frontend-каталоги и действующая проверка ролей (6 passed):

