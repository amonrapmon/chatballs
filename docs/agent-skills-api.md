# Библиотека навыков: административный API

Основание: ADR-0036, SPEC-0035 R-1–R-5, R-28, R-34. Это серверная часть
T-157: библиотека и явные подключения. UI, загрузка моделью, обработчик
шаблонов и готовый навык поставляются отдельными задачами. Штатные AI-ответы,
создание агентов, сообщения и история не меняются.

Подключение инструкционных навыков к живому и проверочному ходу (T-158)
описано в [контракте runtime](agent-skills-runtime.md).

## Доступ и адреса

База: `/api/v1/organizations/{organizationPublicId}/skills/`.
Все операции, включая чтение, доступны только активным OWNER/ADMIN этой
организации. EMPLOYEE/SUPERVISOR доступа не имеют. Публичных маршрутов
библиотеки в API виджета нет. Применяется штатная session/CSRF-аутентификация.

| Метод и путь относительно базы | Назначение |
| --- | --- |
| GET `?q=&page=&pageSize=` | Поиск по названию/условию применения, страницы |
| POST | Создание всей конфигурации |
| GET `{skillId}/` | Полная конфигурация |
| PUT `{skillId}/` | Атомарная замена всей конфигурации |
| GET `{skillId}/deletion/` | Метаданные для подтверждения удаления |
| DELETE `{skillId}/` | Удаление текущей конфигурации и всех её связей |
| PUT `{skillId}/agents/{agentId}/` | Явное подключение |
| DELETE `{skillId}/agents/{agentId}/` | Отключение только этого агента |

`skillId` — стабильный UUID. `agentId` — ID карточки агента (Channel), как в
`agents/`; `aiAgentId` в ответе — технический ID AIAgent. Навык не подключается
автоматически. Один навык допускает несколько агентов и наоборот.

## Сохранение

POST принимает:

```json
{
  "requestId": "b59be3c3-ea8f-49f2-af5c-119f04cd3a28",
  "configuration": {
    "name": "Уточнение обращения",
    "description": "Когда для ответа нужен номер обращения",
    "instruction": "Запросите недостающий номер перед поиском.",
    "templates": []
  }
}
```

PUT принимает тот же объект плюс обязательный `expectedRevision` (целое
положительное число). Частичного PATCH конфигурации и дочерних записей нет.
Неизвестные/пропущенные поля отклоняются. Название: 1–60 символов, условие:
1–200, инструкция: 1–32768; пробельная строка не считается заполнением.
Название/условие обрезаются по краям, инструкция сохраняется буквально.
Нулевые символы и некорректный Unicode отклоняются как `invalid_field`.
Тело изменяющего запроса ограничено 160000 байт до разбора JSON.

В этой задаче `templates` обязателен и равен `[]`; непустой список получает
`templates_unavailable`, без сохранения остальных частей. Точка расширения —
`skills_validation.configuration` и транзакция `save_configuration`: будущая
реализация проверяет весь набор схем/исходников и сохраняет его вместе с
инструкцией. Произвольный JSON шаблонов не сохраняется без проверки.

Ответ POST: 201, повтор: 200; PUT: 200, тело `{"skill": {...}}`.
Ошибка в любой части откатывает конфигурацию, ревизию, аудит и запись запроса.
Успешный PUT повышает ревизию на единицу. Устаревшая ревизия даёт 409
`revision_conflict`; клиент сохраняет локальный ввод и предлагает обновление.
Максимальная ожидаемая ревизия — `2^63-1`.

`requestId` — UUID, уникальный в организации для всех сохранений. При повторе
нужно передать исходное тело и тот же ключ. Создание возвращает тот же ID
и актуальную конфигурацию; повтор PUT не повышает ревизию и не дублирует аудит.
Если после этого PUT объект снова изменили, повтор возвращает конфликт
ревизии. Повтор ключа с другим телом/операцией даёт 409 `request_conflict`.
После удаления повтор создания с прежним ключом возвращает 404 `not_found`
и не воссоздаёт объект. Для нового действия нужен новый ключ.

## Ответы и удаление

Список использует общий контракт `items`, `page`, `pageSize`, `total`,
`pageCount`: по умолчанию 20 записей, максимум 100; выход за последнюю страницу
возвращает последнюю. Поиск регистронезависимый, до 200 символов; порядок —
название, UUID. Поиск применяется до пагинации.

Каждый элемент: `id`, `name`, `description`, `revision`, `templates`,
`templateCount`, `agents` (`id`, `aiAgentId`, `name`), `agentCount`,
`createdBy`/`updatedBy` (`id`, `name`, либо null после удаления автора),
`createdAt`/`updatedAt` (ISO 8601). GET карточки/ответ сохранения дополнительно
содержит `instruction`. Список и подтверждение инструкции не раскрывают.

PUT/DELETE подключения и DELETE навыка принимают `{"expectedRevision": 1}`.
Создание/удаление фактической связи повышает ревизию и пишет аудит. Повтор
подключения/отключения, когда желаемое состояние уже достигнуто, — успешная
операция без изменения ревизии и аудита. Неизвестный/чужой агент даёт 404.

GET `deletion/` возвращает `{"skill": <метаданные>, "confirmationRequired": true}`:
клиент показывает название, список/число агентов и шаблонов, затем передаёт
показанную ревизию в DELETE. Новое подключение между подтверждением и удалением
вызовет конфликт. Успешный DELETE возвращает 204. Аудит и ключи запросов
сохраняются. У Message нет FK на эту конфигурацию: удаление не затрагивает
готовые сообщения и не пересобирает историю.

## Ошибки, изоляция и структура

Ошибки библиотеки: `{"code": "...", "detail": "...", "errors": [{"path": "name",
"code": "invalid_field", "detail": "..."}]}`. `errors` присутствует для поля.
Пояснения используют RU/EN-каталог; исходный ввод в ответ не включается.
Коды: `invalid_request`, `invalid_configuration`, `invalid_field`,
`invalid_revision`, `invalid_request_key` (400), `forbidden` (403),
`not_found`/`agent_not_found` (404), `revision_conflict`/`request_conflict` (409),
`request_too_large` (413), `templates_unavailable` (400). До входа в библиотеку
штатный tenant middleware скрывает недоступную организацию через 404.

Сервисы повторно проверяют полномочия, независимо от HTTP. Все записи
используют tenant-транзакцию и единый порядок блокировок: организация, навык.
Это сериализует конкурирующие сохранения/повторы в одной организации.
БД дополнительно обеспечивает уникальность пары навык–агент, неизменность
UUID/владельца навыка, tenant FK для связей/авторов и FORCE RLS трёх таблиц.
Runtime app не владеет таблицами и не обходит RLS; platform доступа не имеет.

Аудит: `ai.skill_created/updated/deleted/attached/detached`; исполнитель,
организация, UUID навыка, ревизия и ID затронутых агентов. Названия, инструкции,
шаблоны и клиентские данные в payload не записываются. Идемпотентность хранит
ключ, HMAC отпечатка тела, UUID результата и ревизию, без исходного содержимого.
Runtime не может менять/удалять эти ключи.

Модули разделены: модели, валидация, запросы/метаданные, транзакционные сервисы,
HTTP и маршруты. Проверки: `test_skills_api`, `test_skills_access`,
`test_skills_concurrency`, `test_skills_rls`; только они и затронутый каталог
i18n запускаются с `--reuse-db`. RLS проверяется под реальной ролью БД.
