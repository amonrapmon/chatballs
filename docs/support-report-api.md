# Показатели поддержки и экспорты

Штатный доступ и разрешённые справочники для супервизорского UI:
[контракт T-144](supervisor-team-results-ui.md). Строки отчёта дополнительно
содержат `waitingReplies` из текущей управленческой области.

Серверная реализация SPEC-0030 R-2–R-9. Новый интерфейс не входит в задачу.

Политика SPEC-0028 R-8 согласована владельцем: незакрытый рабочий интервал
обрезается по времени блокировки; после блокировки время не накапливается.

## Маршруты

Относительно `/api/v1/organizations/{organization_public_id}/conversations/`:

- `GET support-report/` — JSON;
- `GET support-report.csv` — CSV UTF-8 с BOM;
- `GET support-report.xlsx` — XLSX с числовыми ячейками.

Все маршруты вызывают `calculate_support_report`. Экспортеры только переводят
готовый ответ в таблицы: параметры, показатели и интервалы.

Дополнительные секции `customerRatings` и `qualityAnalysis` возвращаются в
сводке и каждой строке `employees`. Они содержат `state`, `count`, `groups` и
`details`; это наблюдаемые сохранённые результаты, независимо от полноты
событийных длительностей. `available` с нулевым count означает отсутствие
полученных результатов в выбранной области и периоде, а не нулевую оценку.
Выключение функции не удаляет ранее полученные результаты из отчёта.

Клиентские оценки отбираются по `received_at` в `[from,to)`; качество — по
времени CLOSED. `periodBasis` явно указывает это различие. Группа, подключение
и транспорт берутся из соответствующего CLOSED. Фильтр сотрудника и строки
сотрудников используют отвечавших: неизменяемый `responder_ids` запроса оценки
и авторов OPERATOR в снимке публичной истории анализа. Назначение, закрытие,
участие и внутренний комментарий сами по себе не приписывают результат.
Один результат учитывается в сводке один раз; строки ответивших пересекаются
и не суммируются. `responderIds` раскрывает только сотрудников разрешённой
команды; отсутствие старого membership не исключает результат из сводки.

Клиентские `groups` используют тот же `scaleId` и точный снимок шкалы, что и
API оценок; подписи входят в идентичность шкалы. Качество разделяется по
`criteriaVersionId` и коду критерия, даже если шкалы двух версий совпадают.
Возвращаются распределения исходных `originalValues` и действующих
`effectiveValues` со значениями исходного типа и количеством. Общего среднего
и автоматической нормализации нет. Последняя корректировка критерия меняет
только effectiveValue; исходное заключение не изменяется.

T-141 добавляет согласованные серверные `scaleSummaries` и `versions`:
средние внутри точного снимка шкалы/критерия, отдельный набор отправленных
запросов для доли ответивших, отсутствие оценки и статистику корректировок.
Формулы и метаданные описаны в [контракте UI отчёта](support-feedback-report-ui.md).
Существующие groups/details и их основания периода сохраняются.

`qualityAnalysis.revisionPolicy = latest_per_completion`: для каждого
завершения выбирается последняя ревизия анализа. Её состояние и ревизия видны
в details, а `states` показывает WAITING/RUNNING/SUCCEEDED/FAILED. Пока новая
ревизия не успешна, предыдущая оценка не подставляется; распределения содержат
только сохранённые заключения выбранной ревизии. Источник `quality/report/`
сохраняет прежний контракт со всеми ревизиями для отдельного просмотра.

Обычный EMPLOYEE по-прежнему получает собственные базовые показатели, но обе
управленческие секции имеют `state=forbidden`, `count=null`, пустые groups и
details. Супервизор получает только текущую область контроля. API и файлы
имеют одинаковые границы, включая totals и отфильтрованные responderIds.
Экспорты дополнены сводкой оценок, распределениями шкал и деталями результатов;
метаданные периода и фильтров общие, periodBasis и revisionPolicy сохранены.
Шкалы и составные заключения записаны JSON, количества — числовыми ячейками.
Комментарии и значения строковых шкал проходят штатную защиту от формул.

Обязательные параметры: `from`, `to` (ISO 8601 с UTC offset), `timezone`
(IANA, например `Europe/Moscow`). Интервал полуоткрытый `[from,to)`.
Необязательные: `employee` (ID пользователя), `group`, `connection` (ID
подключения), `transport` (`WEB`, `EMAIL`, `TELEGRAM`, `MAX`, `VK`). Скрытая
модель Channel не является фильтром транспорта. Неизвестные, повторные и
некорректные параметры дают 400; недоступные измерения — 404.

Границы задаются конкретными моментами; сервер не прибавляет фиксированные
сутки. При смене UTC offset сутки могут иметь 23 или 25 часов. Возвращаемые
границы нормализованы в UTC, выбранный часовой пояс сохранён отдельно.

## Права

Права перечитываются на каждом расчёте, в том числе при прямом сервисном вызове.
OWNER/ADMIN получают текущую видимую область организации. SUPERVISOR получает
только диалоги своих текущих подконтрольных групп; обычное рабочее участие
не расширяет управленческий отчёт. EMPLOYEE должен явно выбрать собственный
`employee`; командный отчёт ему не выдаётся.

Сотрудники в строках — текущие membership организации; у супервизора — только
участники подконтрольных групп. Фильтр группы для показателей обращений
применяется к историческому снимку, а не сегодняшнему членству сотрудника.
Отсутствующий в разрешённой команде ID сотрудника
в деталях заменяется `null`; числовые totals по разрешённым обращениям сохраняются.
Текущая доступность диалога проверяется до чтения исторических фактов.
Историческое измерение не создаёт доступ. Архивы подчиняются существующему
селектору видимости; физическое удаление исключает факты из отчёта.

## Формулы

`accepted` и `completed` — уникальные ID диалогов с соответствующим событием
в периоде. Назначение без ACCEPTED не увеличивает принятые обращения.
`transferred` — количество событий TRANSFERRED; для строки сотрудника
это исходящие передачи, ответственный перед передачей берётся из прошлых фактов.
`receivedTransfers` — передачи с ненулевым новым ответственным. Итоги не
складываются из строк сотрудников: один диалог может быть принят несколькими.
Публичные ответы сотрудников и AI имеют отдельные счётчики.

`waiting` — от QUEUE_ENTERED до ACCEPTED, выхода к AI или закрытия;
выход из очереди в той же операции claim заканчивается моментом ACCEPTED.
`handling` — от ACCEPTED до смены ответственного, очереди, выхода к AI или
закрытия. Новое назначение само по себе не начинает обработку. Участники
не добавляют время обработки и не увеличивают нагрузку.

`firstResponse` — от начала данного ожидания человека до его первого
публичного ответа; автор ответа и ответственный обработки могут различаться.
`subsequentResponse` — от первого неотвеченного входящего после первого
человеческого ответа до следующего человеческого ответа. Повторные входящие
не сдвигают начало; ответ AI не гасит ожидание человеческого ответа.
`aiResponse` учитывается отдельно по наблюдаемым входящим и фактам AI.
Внутренние комментарии и системные сообщения не входят в публичные ответы.

Для длительности учитывается пересечение с периодом. Неоконченные интервалы
ограничены `min(to, generatedAt)` и имеют `current=true`. `seconds` — сумма,
`meanSeconds` — среднее по пересечённым интервалам ответа; `samples` — их
число, `currentIntervals` — число незавершённых на верхней границе. При
отсутствии измерений ответа сумма и среднее равны `null`, не нулю.
Измерения берутся из фактов начала интервала; для событий — из самого факта.

`currentLoad` — текущие OPEN с назначенным ответственным на момент запроса;
не историческая нагрузка выбранного периода. Для неё группа, подключение и
транспорт — текущие, для исторических показателей — снимки событий.

`employees[].workStatuses`, `workStatusTotals`, `workStatusDetails` содержат
время READY, BUSY, BREAK и UNAVAILABLE в секундах, полноту и интервалы.
Начало — явный переход статуса; конец — следующий переход, блокировка либо
верхняя граница периода/запроса. Блокировка атомарно сохраняет точный
`stopped_at` в переходе текущей версии, не меняя выбранный статус. Разблокировка
и повтор того же статуса не возобновляют завершённый интервал; новый переход
начинает новый интервал. Время в промежутке не приписывается UNAVAILABLE.
Повторная блокировка той же версии не сдвигает первоначальный конец.

Командное время ограничено текущей разрешённой командой супервизора и текущим
составом выбранной группы. Группа в показателях диалога остаётся исторической;
строка сотрудника может иметь `workStatuses.included=false`, если он покинул
выбранную группу. Транспорт и подключение фильтруют обращения и нагрузку,
но не распределяют рабочее время сотрудников по обращениям. У времени
статусов собственная полнота: отсутствие первого выбора означает `null`.
Общие значения становятся `null`, если история хотя бы одного включённого
сотрудника неполна; наблюдаемая сумма сохранена отдельно.

## Полнота и экспорт

Граница хранилища `available_from` не доказывает подключение источников.
Миграция отчётности отдельно фиксирует консервативную дату
`sources_available_from`, когда все необходимые источники присутствуют.
Повторный migrate её не сдвигает. Это timestamp, не восстановление старых фактов.

`statusStopsAvailableFrom` отдельно фиксирует начало устойчивой записи
окончания рабочих интервалов при блокировке. Для уже заблокированного
membership сохраняется существующий точный `blocked_at`; прежние блокировки
после разблокировки не восстанавливаются из presence или приблизительного
времени аудита. Выборы статуса до внедрения устойчивого окончания не выдаются
за полную историю: отчёт считает подтверждённые переходы после этой границы.

`coverage` содержит доступную дату, полноту и ID видимых обращений с неполной
историей. Период до границы и обращения, начавшиеся до неё, делают отчёт
неполным. При неполной истории `values` содержит `null`, а известная часть
выдаётся отдельно в `observedCounts` / `observedSeconds`. Наблюдаемая часть
не выдаётся за полную. Presence, текущий статус и старые сообщения не
восстанавливают отсутствовавшие передачи, принятия или рабочее время.

Все файлы содержат период, часовой пояс, фильтры, единицы и полноту.
Отсутствие обозначено локализованным «Нет данных» / «Unavailable».
CSV экранирует опасные строковые префиксы апострофом. XLSX принудительно
записывает все строки как строки, не формулы, на каждом листе; числа и
логические значения сохраняют свои типы. Тексты берутся из ru/en каталога.
Добавлены отдельные листы/разделы полноты рабочих статусов и их интервалов;
они подчиняются тем же правам и защите строк, что остальные листы.

## Проверка на существующей базе

После штатной сборки/миграций через Skaro:

```powershell
docker compose exec -T backend-admin python manage.py verify_support_exports
```

Команда выбирает уже существующую организацию с обращениями и действующего
управляющего сотрудника. Можно задать `--organization-id`. Все запросы выполняются
в READ ONLY транзакции PostgreSQL; команда не входит в аккаунт, не меняет
сессии, права или учётные данные, не создаёт seed. Сравниваются API, CSV и XLSX
с одинаковыми параметрами, включая фильтры сотрудника, группы и подключения.
Отдельные HTTP-запросы имеют разные `generatedAt`; сравнение исключает только
момент формирования файла. Период, полнота, единицы, числа и детали совпадают.
