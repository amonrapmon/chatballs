# Внутренние комментарии в рабочем месте

Интерфейс к [API внутренних комментариев](internal-comments-api.md): выбор
аудитории в редакторе и запись комментария в ленте диалога. Макет —
`design/baseline/platform-expansion/`: `Чат · состояния.dc.html` (C1–C4),
`Чат · совмещённые кадры.dc.html` (K1–K2, M1), `Редактор ответа.dc.html`.

## Редактор

Над полем — вкладки «Ответ клиенту» и «Комментарий», рядом подпись, кому уйдёт
текст: «Увидит клиент · канал» или «Только сотрудники — клиент не увидит».
Аудитория выбирается до отправки и задаёт маршрут запроса:

| Вкладка | Запрос | Что происходит |
|---|---|---|
| Ответ клиенту | `POST …/conversations/{id}/messages/` (файл — `…/attachments/`, голос — `…/voice/`) | сообщение уходит клиенту, диалог переходит к сотруднику |
| Комментарий | `POST …/conversations/{id}/comments/` с `audience: "INTERNAL"` | запись видят только сотрудники; ответственный и режим диалога не меняются |

Состояния вкладок не смешиваются:

- у комментария нет эмодзи, вложения и голосового; выбранное для ответа вложение
  к комментарию не прикладывается и возвращается вместе с вкладкой ответа;
- предупреждение «сообщение перехватит диалог» показывается только у ответа
  клиенту — комментарий диалог не перехватывает;
- ошибка сохранения комментария видна только на вкладке комментария, ошибка
  отправки ответа — только на вкладке ответа;
- пока запрос в пути, вкладка не переключается.

Текст поля у вкладок общий. Если с набранным текстом перейти с комментария на
ответ клиенту, под редактором появляется напоминание, кто теперь увидит текст.

При сбое сохранения текст остаётся в поле, под редактором — причина и
«Повторить». Повтор того же текста уходит с прежним `operationId`, поэтому
потерянный ответ сервера не создаёт второй комментарий.

Заблокированные состояния редактора (диалог закрыт, диалог ведёт другой
сотрудник) прежние: вкладки в них не показываются.

Вкладка «Письмо» из макета появится вместе с отправкой писем из диалога.

## Лента

Сообщения и комментарии загружаются двумя независимыми окнами со своими
курсорами (`useHistoryWindow`) и сливаются в одну ленту по времени создания
(`feed.ts`). Пока одно из окон не догружено вверх, строки второго раньше его
границы не показываются; прокрутка вверх догружает то окно, которое держит
границу.

Новые комментарии приходят по событию сокета `comments.changed`; опрос
остаётся страховкой, как и у сообщений.

Комментарий стоит среди реплик сотрудников: аватар автора (фото из
`author.avatarUrl` или инициалы), тёплый фон, пунктирная рамка, замок и
«внутренний комментарий» в подписи, без отметки доставки. Редактирования,
удаления и вложений нет.

## Проверка

```sh
docker compose exec -T frontend sh -c "cd /app/apps/internal-ui && npx tsc -p tsconfig.json"
docker compose exec -T frontend sh -c "cd /app/apps/internal-ui && npx vitest run src/features/conversations/feed.test.ts src/features/conversations/historyScrollState.test.ts src/features/conversations/useConversationEvents.test.tsx src/features/conversations/timeline.test.ts src/i18n/catalog.test.ts"
```

Браузерная проверка идёт со штатным бэкендом: два сотрудника в разных сеансах
обсуждают диалог комментариями, клиент в веб-виджете видит только ответ. В
dev-окружении виджет открывается через сервис `gateway` (`/chat/?widgetKey=…`),
а адрес шлюза должен входить в разрешённые домены точки входа.
