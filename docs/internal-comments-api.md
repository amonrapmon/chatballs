# API внутренних комментариев

Маршрут: `/api/v1/organizations/{organization_public_id}/conversations/{id}/comments/`.
Использует обычную аутентификацию сотрудников и tenant-контекст организации.

## Создание

`POST` принимает объект:

```json
{
  "audience": "INTERNAL",
  "text": "Текст внутреннего обсуждения",
  "operationId": "01900000-0000-4000-8000-000000000001"
}
```

Все три поля обязательны. Текст — непустая строка до 10 000 символов;
краевые пробелы удаляются. `operationId` — UUID, уникальный в организации.
Автор и время берутся на сервере; переданные клиентом `authorId` и `createdAt`
не используются. Новая запись возвращает `201`, точный идемпотентный повтор —
`200` и ту же запись. Повтор проверяет текущий доступ заново. Тот же ключ с
другим текстом, автором или диалогом возвращает `409`, не изменяя старую запись.
Конкурентные повторы разрешаются уникальным ограничением в PostgreSQL.

Ответ: `{"comment": {...}}`. Запись содержит `id`, `conversationId`,
`audience`, `text`, `author: {id, name, avatarUrl}`, `createdAt` (ISO 8601),
`operationId`. `avatarUrl` — ссылка на фото автора в текущей организации или
`null`, если фото нет; так же отдаётся автор сообщения сотрудника.
Создание не назначает ответственного и не меняет режим управления, ожидание
ответа или доступность сотрудника; не создаёт клиентское сообщение, внешнюю
отправку, уведомление клиенту или ход AI.

## История

`GET` принимает `limit` (по умолчанию 50, максимум 200), `before` или `after`.
Без курсора возвращает последние записи в хронологическом порядке.
`before` продолжает историю к старым записям, `after` — к новым.
Ответ: `{"items": [...], "hasMore": true, "cursor": 123}`.
При `hasMore=true` курсор предназначен для следующего запроса в том же
направлении. Курсор принадлежит только истории комментариев этого диалога;
история сообщений использует отдельный endpoint и отдельные идентификаторы.
Не найденный в доступном наборе курсор обрабатывается штатным `window`:
возвращается начальное окно в выбранном направлении.

Редактирование и удаление отсутствуют; `PATCH` и `DELETE` возвращают `405`.
Существующая заметка диалога остаётся отдельной изменяемой функцией.

## Доступ и realtime

Чтение требует `conversations.view`, создание — `conversations.operate`, а
также действующей membership и доступа к конкретному диалогу. Используется
существующая ролевая политика и видимость по группе, назначению или управлению;
активное участие даёт доступ только к своему диалогу. Завершение участия
отнимает это основание доступа; остальные основания сохраняются.
Роли без соответствующего права получают отказ; API не вводит новую роль.
Недоступный или чужой диалог возвращает `404`.

Штатный сокет сотрудников
`/ws/organizations/{organization_public_id}/conversations/` после `watch`
получает `{"type":"comments.changed","conversationId":123}`. Событие
публикуется только после коммита новой записи, без текста, автора и ключа
операции. Повтор и откат транзакции события не создают. Получатель заново
проверяется перед каждой доставкой в tenant-транзакции: текущая роль,
membership, глобальная активность, группа, назначение и участие. При потере
доступа подписка снимается. Событие не отправляется в общий inbox, виджет,
клиентские уведомления или внешние транспорты.

## Самостоятельная серверная проверка

В штатном окружении Skaro с запущенными `postgres`, `redis`, `backend-app`
и `backend-admin`:

```sh
docker compose build backend-app backend-admin
docker compose exec -T backend-admin python manage.py check
docker compose exec -T backend-admin pytest -q --reuse-db chatballs/conversations/test_comment_api.py chatballs/conversations/test_comment_concurrency.py chatballs/conversations/test_comment_realtime.py chatballs/conversations/test_comment_guards.py chatballs/conversations/test_comment_history.py chatballs/conversations/test_comment_public_effects.py chatballs/conversations/test_internal_ai_history.py chatballs/conversations/test_realtime.py chatballs/webchat/test_internal_record_access.py chatballs/i18n/tests.py::CatalogTests
```

Проверки работают с отдельной тестовой PostgreSQL-базой. Тесты комментариев
realtime используют реальный Redis канального слоя, без подмены backend.
Новый UI для приёмки не нужен.
